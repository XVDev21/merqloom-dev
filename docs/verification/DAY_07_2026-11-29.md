## Store to native Admin walkthrough

On the fresh browser database, `scripts/mq104-store-browser.js` selected one Natural tray and completed the accepted Store checkout. Store confirmation displayed synthetic demo order **#1**, Natural × 1, item subtotal PHP 450, simulated shipping PHP 10, tax PHP 0 and total PHP 460. It disclosed simulated payment and shipping. Native Admin's order #1 showed the same variant, quantity and totals. Its payment was **Authorized** by the system provider, with PHP 0 paid and PHP 460 outstanding; this is a demo payment state, not a real charge.

In native Admin, open Orders → #1 → Unfulfilled Items → **Fulfill items**. Select **Demo warehouse**, **Simulated shipping** and the full quantity of 1. Turn **Send notification** off, then create the fulfillment. On Fulfillment #1, choose **Mark as shipped**, enter fictional tracking `SIMULATED-MQ104` and reserved `example.test` links, turn notification off and save. The final native card shows one shipped fulfillment, one Natural item, Demo warehouse and the Manual provider. No carrier interaction or customer notification was performed.

The table uses the native inventory level and the Store's channel availability; the preflight and integration test checked both. The Admin fulfillment form showed **Available 12** for this order while channel availability was 11. The installed Admin calculation adds this line's own reserved unit back to the unreserved availability (11 + 1); it is the quantity usable for this fulfillment, not a second stock balance.

The same browser order had one `order_cart` link, one full-quantity fulfillment and one fictional tracking label. Authenticated replays of `POST /admin/orders/:id/fulfillments` and `POST /admin/orders/:id/fulfillments/:fulfillment_id/shipments` each returned HTTP 400; the fulfillment, shipment timestamp, label and inventory were unchanged. A separate native preflight observed the same sequence with no label and the same results. No duplicate side effect or inventory inconsistency was observed.

The integration case creates a unique test-only direct-stock tray with three units through native workflows, and drafts it in cleanup. A request for four units was rejected before order creation with no order, fulfillment or inventory change. Unauthenticated fulfillment and shipment requests returned HTTP 401 and left the native records and stock unchanged. The test checks the actual reservation row, order item quantities, selected location, provider, fulfillment item, shipment label and replay state. It runs serially through root `pnpm test` and does not depend on earlier tray reservations.
