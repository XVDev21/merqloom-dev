## Schema and workflow contract

The `supplier` module owns a supplier ID, unique active fixture code and name, and `supplier_mapping` records with a supplier relation and external SKU. The generated migration has a **non-partial PostgreSQL unique index** on `(supplier_id, external_sku)`; the key remains reserved even when a mapping is soft deleted. Medusa's default unique-code index is scoped to active suppliers. The native module link allows multiple mappings per Product Variant and at most one variant per mapping. The link is the only persisted variant association.

`createSupplierMappingWorkflow` validates and trims its inputs with the pinned framework's Zod, preserves SKU case, resolves the supplier and native variant, and requires the variant's product to have `metadata.source === 'supplier'`. It creates the mapping once and uses Medusa's link step. Its compensating step dismisses any attempted link before deleting the new mapping. It does not alter native catalog, stock, orders or fulfillment. Repeated import and upsert behavior is outside this operation.

## Offline adapter contract

The typed `SupplierAdapter` returns `{ok:true, value}` or `{ok:false, reason}`. `getCatalog` returns fixture SKU/title rows. `getInventory` accepts a supplier, at most 100 requested SKUs and an explicit UTC timestamp; it returns matching observations with the supplied timestamp, including known quantity zero, and omits unknown SKUs. `submitFulfillment` accepts a nonempty bounded list of known SKUs and positive safe-integer quantities and returns a simulated receipt. Its reference is a deterministic SHA-256 of the supplier code and stable request key. `getFulfillmentStatus` validates that receipt for the same supplier and returns simulated `accepted` status. Unknown suppliers, unknown fulfillment SKUs, invalid inputs and invalid receipts have typed rejections.

Fixtures `fictional-north` and `fictional-south` each contain `POUCH-NATURAL`; North also contains zero-stock `POUCH-ZERO`. The adapter has no network or persistence and makes no native stock or fulfillment writes. A receipt is a deterministic mock value, not proof of an external request; MQ-203 owns durable receipt storage, request-key conflict handling and retries. Supplier observation persistence, freshness and eligibility remain MQ-202 work.

## Limits

This work adds no CSV import, observation storage or freshness enforcement, supplier checkout, durable retry worker, Admin UI, real supplier calls or deployment. The pouch remains browse-only at zero native availability. Mock receipt validation is deterministic and local; it is not an authentication mechanism or durable fulfillment record. MQ-202 requires a separate release.
