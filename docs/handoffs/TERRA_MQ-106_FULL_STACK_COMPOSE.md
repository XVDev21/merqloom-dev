## Implementation contract

### 1. Default Compose stack and startup

- [ ] Extend `compose.yaml` with `backend` and `storefront`. Keep the existing PostgreSQL and Redis definitions, data mounts and published loopback ports. Publish Studio/Store at `127.0.0.1:18000` and Medusa/Admin at `127.0.0.1:19000`. Keep PostgreSQL at `127.0.0.1:15432` and Redis at `127.0.0.1:16379`. Apps listen on container interfaces. Internal clients use Compose DNS and internal ports. Browsers use mapped host URLs. Keep the existing Admin auth, CORS and local HTTP checkout cookie semantics.
- [ ] Make initial setup work with `make start` and document the equivalent Compose setup. Once the app containers exist, starting or restarting the project from Docker Desktop must recover all four services with no host app processes. Containers need bounded readiness waits or retries for both initial Compose creation and an existing-container stop/start, where dependency conditions alone may be insufficient. Before the new containers exist, the Desktop Start action only starts the current project containers. [Compose start and up](https://docs.docker.com/compose/support-and-feedback/faq/) · [Startup ordering](https://docs.docker.com/compose/how-tos/startup-order/)
- [ ] Run the existing Medusa migration and seed path on a fresh local database and verify a safe repeat on a populated disposable copy. Keep startup idempotent and fail clearly when initialization fails. Reuse the existing development key lookup or Medusa facilities to let the Store access the seeded channel automatically. Keep PostgreSQL credentials out of the storefront container. Keep secret values, runtime env files and generated data out of logs, Git and image layers. Keep existing JWT, cookie and MFA material stable where already configured. Separate local bootstrap from production release migrations and demo seeding.
- [ ] Add useful service health checks and verify readiness through the live native Store API and the storefront catalog in addition to process liveness. Keep both app logs visible in Docker Desktop and via `docker compose logs -f backend storefront`. Preserve sanitized diagnostics and avoid raw checkout IDs, customer data, tokens and error payloads.

### 2. Hot reload and portable images

- [ ] Run the existing framework development servers in the development containers with source bind mounts or an equivalent mechanism that works after a Desktop project start. Keep platform-specific dependencies and generated build output inside the container or container-owned volumes. Demonstrate one scoped Next.js edit and one Medusa edit picked up without an image rebuild. Document the rebuild path for lockfile or dependency changes. Restore the verification edits before commit.
- [ ] Build separate production runtime images using multi-stage builds and the locked workspace. Production starts with runtime-provided ports, database and Redis URLs, browser-facing origins as applicable, and server-only configuration. Keep host loopback assumptions, development mounts, local HTTP cookie overrides, and demo initialization out of the default production image command. Verify both images can start against externalized disposable backing services without host source or developer env-file mounts. Document the runtime contract for future container hosts. Keep provider-specific manifests, registry publication, deployment, infrastructure as code and cloud secrets outside this PR. [Docker multi-stage builds](https://docs.docker.com/build/building/multi-stage)
